# Data Model: Child Device QR Scan & Pairing

**Spec**: 017-child-qr-scan | **Date**: 2026-06-12

---

## New Database Functions (Phase 0 Migration)

### `public.consume_pairing_token(p_token UUID, p_family_id UUID)`

SECURITY DEFINER PostgreSQL function callable via anon key. Atomically validates the token UUID + family_id match, creates a minimal child profile, and marks the token consumed.

**Returns**: `json` — `{ success, child_id, family_id }` on success; `{ success, error }` on failure.

**Error codes**:
- `invalid_token` — token not found, already consumed, expired, or family_id mismatch
- `parent_not_found` — no parent profile exists for the given family_id

**Permissions**: `GRANT EXECUTE TO anon` — callable without authentication.

---

### `public.consume_pairing_token_by_code(p_manual_code TEXT)`

SECURITY DEFINER PostgreSQL function for manual 6-digit code entry. Looks up the token by `manual_code` (globally, within the active window). Creates the child profile atomically.

**Returns**: same shape as `consume_pairing_token`.

**Permissions**: `GRANT EXECUTE TO anon`.

## Existing Table Modifications

No new tables are created in Phase 2. The existing `profiles` and `pairing_tokens` tables (from Phase 1 migration `20260611000001_two_device_schema.sql`) are sufficient.

### `profiles` — child row added by RPC

When `consume_pairing_token` succeeds, it inserts a row with:

| Column | Value |
|--------|-------|
| `id` | `gen_random_uuid()` (new UUID, NOT linked to auth.users) |
| `role` | `'child'` |
| `parent_id` | parent profile's `id` (found via `family_id`) |
| `family_id` | from the consumed token |
| `full_name` | `''` (empty — parent fills in later) |
| `is_active` | `true` |
| `pin_hash` | `NULL` initially; updated via `child-setup-pin.tsx` (fire-and-forget) |
| `pin_length` | `6` (updated alongside `pin_hash`) |

### `pairing_tokens` — updated on consumption

| Column | Change |
|--------|--------|
| `used_at` | Set to `NOW()` |
| `child_id` | Set to new child profile UUID |

## Local Device Storage (AsyncStorage)

### `@child_pairing_state`

JSON-serialized `ChildPairingState` object. Written once on successful token consumption; persists across app restarts (FR-019).

```typescript
interface ChildPairingState {
  child_id: string;    // UUID of the new child profile row
  family_id: string;   // UUID of the parent's family
  parent_id: string;   // UUID of the parent's profile row
  paired_at: string;   // ISO 8601 UTC timestamp
  has_pin: boolean;    // true once @child_pin_hash is also saved
}
```

### `@child_pin_hash`

Hex string — SHA-256 hash of the 6-digit PIN. Written on PIN creation in `child-setup-pin.tsx`. Used for offline PIN verification on subsequent app opens.

## Existing Schema Context (unchanged)

The `pairing_tokens` table (Phase 1):
- `token UUID UNIQUE` — the QR payload's `token` field; looked up by `consume_pairing_token`
- `manual_code TEXT` — the 6-digit display code; looked up by `consume_pairing_token_by_code`
- `family_id UUID` — validated by `consume_pairing_token` (not required by `consume_pairing_token_by_code`)
- `used_at TIMESTAMPTZ NULL` — NULL = available; non-NULL = consumed; triggers Realtime CDC to parent

The `profiles` table (Phase 0 + existing):
- `id UUID PRIMARY KEY` — NOT a FK to auth.users; free UUID generated by RPC
- `parent_id UUID REFERENCES profiles(id)` — self-referencing FK to parent's profile row
- `pin_hash TEXT` — Phase 2 writes here via fire-and-forget; Phase 3 enforces this
