# Implementation Plan: Child Device QR Scan & Pairing

**Branch**: `010-content-seed-initial` | **Date**: 2026-06-12 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/017-child-qr-scan/spec.md`

---

## Summary

A child device that has never been paired opens the app and is routed directly to a "Link to Parent" screen. The child scans the QR code from the parent's Phase 1 pairing screen OR enters the 6-digit manual code. This invokes a SECURITY DEFINER PostgreSQL RPC (`consume_pairing_token`) that validates the token, creates a headless child profile, and marks the token consumed atomically — all in a single server-side call using the anon key. The child then sets a 6-digit PIN (SHA-256 hashed, stored locally in AsyncStorage and synced to `profiles.pin_hash`). The pairing state is persisted locally so subsequent opens go straight to PIN entry. The parent's Realtime subscription (Phase 1) detects the `pairing_tokens.used_at` update and auto-navigates the parent to their dashboard.

## Phase 0 — Database: `consume_pairing_token` RPC

**Migration**: `supabase/migrations/20260612000001_consume_pairing_token.sql`

**Goal**: Two SECURITY DEFINER PostgreSQL functions callable via the anon key. Each atomically validates a token, creates a minimal child profile, and marks the token consumed in a single transaction.

### Function 1 — QR code path (token UUID)

```sql
CREATE OR REPLACE FUNCTION public.consume_pairing_token(
  p_token UUID,
  p_family_id UUID
) RETURNS json
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_token_row pairing_tokens%ROWTYPE;
  v_parent_id UUID;
  v_child_id  UUID;
BEGIN
  SELECT * INTO v_token_row
  FROM pairing_tokens
  WHERE token = p_token
    AND family_id = p_family_id
    AND used_at IS NULL
    AND expires_at > NOW()
  FOR UPDATE;

  IF NOT FOUND THEN
    RETURN json_build_object('success', false, 'error', 'invalid_token');
  END IF;

  SELECT id INTO v_parent_id
  FROM profiles
  WHERE family_id = p_family_id AND role = 'parent'
  LIMIT 1;

  IF v_parent_id IS NULL THEN
    RETURN json_build_object('success', false, 'error', 'parent_not_found');
  END IF;

  v_child_id := gen_random_uuid();
  INSERT INTO profiles (id, role, parent_id, family_id, full_name, is_active)
  VALUES (v_child_id, 'child', v_parent_id, p_family_id, '', true);

  UPDATE pairing_tokens
  SET used_at = NOW(), child_id = v_child_id
  WHERE id = v_token_row.id;

  RETURN json_build_object(
    'success', true,
    'child_id', v_child_id::text,
    'family_id', p_family_id::text
  );
END;
$$;

GRANT EXECUTE ON FUNCTION public.consume_pairing_token(UUID, UUID) TO anon;
```

## Phase 5 — Screen Implementation

### `app/auth/child-scan.tsx` (NEW)

Two views toggled by `mode` state: `'camera'` (default) or `'manual'`.

**Camera view**:
- `const [permission, requestPermission] = useCameraPermissions()`
- If `!permission?.granted`: show "camera unavailable" message + "Enter code manually" button (no camera rendered)
- If granted: render `<CameraView barcodeScannerSettings={{ barcodeTypes: ['qr'] }} onBarcodeScanned={handleScan} />`
- `handleScan(event)`: guard with `isScanning` ref to prevent double-submit → `parseQrPayload(event.data)` → `isTokenExpired(payload)` check → `consumePairingToken(payload.token, payload.family_id)` → on success: `savePairingState(...)` → `router.replace('/auth/child-setup-pin')`

**Manual view** (toggled by "Enter code manually" button):
- `<TextInput>` accepting 6 digits (filters non-numeric; auto-inserts hyphen at position 3 for display)
- Submit → `consumePairingTokenByCode(code, familyId)` where `familyId` comes from QR payload stored in state
- **Problem**: manual code doesn't contain `family_id` — need a separate input for family_id OR require QR scan first to get family_id

Wait — this is a design gap. The manual code (6 digits) corresponds to `pairing_tokens.manual_code`. The `consume_pairing_token_by_code` RPC requires both `manual_code` AND `family_id`. But the child device doesn't know `family_id` unless it scanned the QR first (QR payload contains `family_id`).

**Resolution** (from spec Clarification Q2 in specify session): The clarification answered "Direct Supabase database call following the existing API Hook Pattern." Looking at FR-011: "The manual entry input MUST accept the 6-digit pairing code shown on the parent's screen." The parent's screen shows BOTH the QR (which embeds family_id) and the manual code. For manual entry: the child must enter the 6-digit code; the `family_id` is obtained from the QR payload if scanned first, or the child needs an additional family code if no QR was attempted.

**Pragmatic approach**: The child-scan screen has two sub-states:
1. Camera-first: camera permission denied or not yet scanned → show both QR scanner (if available) and manual code input field; for manual entry, also require the family_id (shown as a separate short field, or encoded into the manual code display format)
2. Alternatively, make `consume_pairing_token_by_code` not require family_id and instead find the token by manual_code globally (within a time window) — simpler UX but slightly weaker security

**Chosen approach for plan**: Manual code entry asks for the 6-digit code AND the `family_id` display. However, to avoid UX complexity, the parent screen will display the family code short-form OR we extend the manual code to include family_id encoded. Per YAGNI, the simplest approach: **alter the RPC to look up by manual_code without requiring family_id** — instead use `expires_at > NOW()` and `used_at IS NULL` to find the unique active token matching the code. Manual codes are short-lived (10 min) and 6-digit, making collisions extremely unlikely.

Update `consume_pairing_token_by_code` signature to drop `p_family_id` requirement:

```sql
CREATE OR REPLACE FUNCTION public.consume_pairing_token_by_code(
  p_manual_code TEXT
) RETURNS json ...
WHERE manual_code = p_manual_code AND used_at IS NULL AND expires_at > NOW()
```

This lookup returns `family_id` from the found token row, so it is still included in the result.

**Updated TypeScript**:
```typescript
consumePairingTokenByCode(manualCode: string): Promise<ConsumePairingTokenResult>
// calls: supabase.rpc('consume_pairing_token_by_code', { p_manual_code: stripped })
```

### `app/auth/child-setup-pin.tsx` (NEW)

6-digit PIN setup (enter + confirm). Pattern from `app/auth/setup-pin.tsx` but:
- 6 dots instead of 4 (`newPin.length < 6`, threshold at 6)
- On match:
  1. `const hash = await Crypto.digestStringAsync(Crypto.CryptoDigestAlgorithm.SHA256, pin)`
  2. `AsyncStorage.setItem('@child_pin_hash', hash)`
  3. `usePairingStore.getState().savePinHash(hash)`
  4. Fire-and-forget cloud sync: `supabase.from('profiles').update({ pin_hash: hash, pin_length: 6 }).eq('id', child_id)` — failure logged but NOT awaited
  5. `router.replace('/(child)')`

### `app/index.tsx` (MODIFY)

Add `usePairingStore` check in mount `useEffect` (before existing auth logic):
