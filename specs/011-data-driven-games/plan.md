# Implementation Plan: Data-Driven Games

**Branch**: `011-data-driven-games` | **Date**: 2026-06-10 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/011-data-driven-games/spec.md`

## Summary

Replaces the hardcoded counting game in `app/(child)/game/[id].tsx` with a data-driven renderer that reads `game_type` and `config_json` from the `content_items` database row. Adds a matching game renderer for `game_type = 'matching'`. Wires activity logging on win. Fixes the `useGame` hook's return type from `ContentItem` to `GameItem`. No database schema changes.

## Technical Context

**Language/Version**: TypeScript 5.9 + React Native 0.83.6 (Expo 55)

**Primary Dependencies**: Expo Router ~55.0.16 (navigation), `@supabase/supabase-js` ^2.x (data hook already exists), React Native Reanimated 4.2.1 (existing animations), `@testing-library/react-native` ^14.0.0 (unit tests)

**Storage**: Supabase PostgreSQL — `content_items` table (no schema changes — read-only)

**Testing**: Jest 29 + ts-jest; `@testing-library/react-native` for component unit tests; `HAS_CREDENTIALS` integration test pattern (same as feature 010)

**Target Platform**: iOS + Android (React Native)

**Project Type**: Mobile app — presentation layer change only

**Performance Goals**: Loading indicator visible within 100 ms of mount (SC-004); no new network calls beyond what `useGame` already makes

**Constraints**: No hardcoded game values in component after change (FR-011); no drag-and-drop (spec Assumptions); offline caching out of scope

**Scale/Scope**: 2 game types, 2 test files, 2 source files modified

## Implementation Phases

### Phase 1 — Setup & CLI Wiring

Add npm scripts to `package.json` before any implementation begins.

```json
"test:game-screen": "jest tests/unit/game/gameScreen.test.tsx --no-coverage",
"test:game-screen-integration": "jest tests/integration/gameScreen.test.ts --no-coverage"
```

### Phase 2 — TDD Gate (write failing tests)

**⚠️ CRITICAL**: Write all tests BEFORE editing the game screen or hooks.

`tests/unit/game/gameScreen.test.tsx` — mock `useGame`, `logGameActivity`, `useLocalSearchParams`, `useRouter`; assert:
- Loading spinner shown when `isLoading = true`
- Error state shown when `error` is set
- Counting game: question text from `config_json.question` appears
- Counting game: each value in `config_json.choices` appears as a button
- Counting game: tapping `correct_answer` button triggers win screen
- Counting game: tapping wrong button shows wrong feedback then resets
- Matching game: each `config_json.pairs[].item` label appears
- Matching game: win state reached when all pairs matched
- Activity log called on counting win
- Activity log called on matching win
- Fallback error state for unknown `game_type`

`tests/integration/gameScreen.test.ts` — HAS_CREDENTIALS skip; fetch real counting game row by title; assert `config_json` has required keys.

Run `npm run test:game-screen` — confirm **all unit tests FAIL** (red state confirmed before implementation).

### Phase 3 — Type Fix (useGame return type)

Edit `services/api/games.ts`: change `useGame` return type annotation from `ApiResponse<ContentItem>` to `ApiResponse<GameItem>`. No runtime logic changes.

### Phase 4 — Counting Game Renderer

Edit `app/(child)/game/[id].tsx`:
1. Replace hardcoded state with `useGame(id)` call
2. Add loading state (ActivityIndicator centred on pink background)
3. Add error state (error text + back button)
4. Extract `CountingConfig` type alias
5. Replace hardcoded question/choices/targetCount with values from `config_json`
6. Replace hardcoded emoji grid with `Image` component from `config_json.image_url`
7. Correct answer → single win transition (1 star); wrong answer → reset (same as before)
8. Remove `level` state, `targetCount` derivation, and level-advance logic

### Phase 5 — Matching Game Renderer

Add matching game renderer within the same `[id].tsx` file:
1. Extract `MatchingConfig` and `MatchingPair` type aliases
2. Implement `selectedLabel` + `matchedItems` + `showWrong` state
3. Render label cards (TouchableOpacity, one per `pair.item`)
4. Render image cards (Image + TouchableOpacity, one per `pair.image`)
5. Handle label tap → set `selectedLabel`
6. Handle image tap → check if `selectedLabel` matches this pair's `item`; if yes → add to `matchedItems`; if no → `showWrong` for 600 ms then reset
7. When `matchedItems.size === pairs.length` → set `won = true`
8. Use same win screen as counting game

### Phase 6 — Activity Logging on Win

In the win transition handlers (counting correct answer + matching all pairs):
1. Import `logGameActivity` and `useAuthStore`
2. Calculate `durationSeconds = Math.round((Date.now() - startedAt) / 1000)`
3. Call `logGameActivity({ childId, gameId: id as string, durationSeconds })` — fire-and-forget

### Phase 7 — Unknown game_type Fallback

Add an `else` branch after counting/matching renderers:
- Show error card: "Game type not supported" + back button
- Satisfies FR-009 and SC-005
