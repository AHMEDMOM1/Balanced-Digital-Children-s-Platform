## Summary

After a parent completes email OTP registration, the app redirects to a new QR Pairing screen instead of the existing PIN setup screen. The screen generates a single-use, 10-minute token, displays it as both a scannable QR code and a `XXX-XXX` text code, auto-regenerates on expiry, and navigates the parent to their dashboard automatically when a child device uses the token.

This plan covers: Phase 0 DB schema, the `services/api/pairing.ts` service module, `app/auth/qr-pairing.tsx` screen, and a one-line change to `app/auth/register.tsx`.

## Phase 0 — Database Schema

**Goal**: New tables and columns that all integration tests depend on.

**Migration**: `supabase/migrations/20260611000001_two_device_schema.sql`

Key operations (all idempotent):
1. `CREATE TABLE IF NOT EXISTS pairing_tokens` (id, family_id, token UUID UNIQUE, manual_code, created_at, expires_at, used_at, child_id)
2. `CREATE TABLE IF NOT EXISTS device_registrations` (id, profile_id, family_id, device_role, device_token, last_seen_at, created_at)
3. `ALTER TABLE profiles ADD COLUMN IF NOT EXISTS pin_hash TEXT`
4. `ALTER TABLE profiles ADD COLUMN IF NOT EXISTS pin_length INT DEFAULT 6`
5. Indexes on pairing_tokens (family_id, token, manual_code) and device_registrations (family_id)
6. `ALTER TABLE pairing_tokens ENABLE ROW LEVEL SECURITY`
7. `ALTER TABLE device_registrations ENABLE ROW LEVEL SECURITY`
8. `DROP POLICY IF EXISTS` + `CREATE POLICY parent_read_pairing_tokens` (SELECT using family_id match)
9. `DROP POLICY IF EXISTS` + `CREATE POLICY parent_write_pairing_tokens` (INSERT with check family_id match)
10. `DROP POLICY IF EXISTS` + `CREATE POLICY service_write_device_registrations` (stub for Phase 2)

**RLS policy expressions** (family_id match via profiles lookup):
```sql
USING / WITH CHECK (
  family_id = (
    SELECT family_id FROM profiles
    WHERE id = auth.uid() AND role = 'parent'
  )
)
```

**Apply script**: `scripts/apply-two-device-schema.ts` (follows pattern of `scripts/apply-migration.ts`)

## Phase 3 — Service Implementation (`services/api/pairing.ts`)

Implement `formatDisplayCode`, `generatePairingToken`, `watchForChildPaired` per contracts/pairing-api.md.

Key implementation notes:
- `generatePairingToken`: INSERT with no explicit token/manual_code (DB defaults generate them); SELECT the returned row; map to `PairingResult`; emit structured log
- `watchForChildPaired`: Postgres Changes on `pairing_tokens`, `event: 'UPDATE'`, `filter: family_id=eq.{familyId}`; call `onPaired` when `payload.new.used_at !== null`; log subscribe/unsubscribe lifecycle
- Error codes: `42501` → `"Unauthorized — parent session required"`; others → `"A network error occurred. Please try again."`

**Confirm GREEN**: `npm run test:pairing` all pass.

## Phase 4 — Screen Implementation

### `app/auth/qr-pairing.tsx` (NEW)

Full implementation per `contracts/pairing-api.md` Screen Contract:
- Read `familyId` from `useAuthStore().parentData?.familyId`; redirect to `/auth/register` if null
- `useEffect` mount: `generatePairingToken` → set state; `watchForChildPaired` → store unsubscribe ref
- `useEffect` countdown: `setInterval(1000)` → update `remainingSeconds`; when 0 → `handleRegenerate()`
- `handleRegenerate`: set `isGenerating = true` → `generatePairingToken` → update state → `isGenerating = false`
- `onPaired`: call stored unsubscribe ref → `router.replace('/(parent)')`
- `useEffect` cleanup: clear interval + call unsubscribe ref
- QR: `<QRCode value={qrPayload} size={220} />` from `react-native-qrcode-svg`
- Manual code: large `<Text>` showing `displayCode ?? '---'`
- Timer: `MM:SS` text, `'--:--'` while `isGenerating`
- Regenerate button: disabled + `<ActivityIndicator />` while `isGenerating`; old codes remain visible
- Error banner: shown when `error !== null`
