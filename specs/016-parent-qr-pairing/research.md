# Research: Parent Device Registration & QR Pairing

**Spec**: 016-parent-qr-pairing | **Date**: 2026-06-11

---

## Decision 1 — QR Code Display Library

**Decision**: Use `react-native-qrcode-svg` to render the scannable QR code on the parent device.

**Rationale**: Pure JavaScript implementation; no native module compilation required; peers with `react-native-svg` which is already installed at version 15.15.3 in this project. Renders the QR as a scalable SVG — correct resolution on all screen densities. The alternative (`expo-barcode-scanner`) is a camera-based scanner only; it cannot generate/display QR codes.

**Alternatives considered**:
- `expo-barcode-scanner` — only for scanning, not display. Needed in Phase 2 on the child device.
- Canvas/base64 approach — more complex, no benefit.

**Install**: `npm install react-native-qrcode-svg`

## Decision 2 — QR Payload Contents

**Decision**: QR encodes `JSON.stringify({ token, family_id, expires_at })` where `token` is the UUID primary key from `pairing_tokens`.

**Rationale**: This is identical to what TwoDevicePlan.md specifies. The `token` UUID alone would suffice for server validation, but including `family_id` and `expires_at` allows the child device to perform an offline pre-validation (reject obviously expired codes before making a network call) and disambiguate tokens across families without a DB lookup. The `family_id` is not a secret — it is already stored in the parent's profile and in subsequent realtime channel subscriptions.

**Security note**: The QR is a single-use token with a 10-minute TTL. Even if a screenshot of the QR is captured, it is unusable after 10 minutes or after first use.

## Decision 3 — Families Table vs family_id Column

**Decision**: Do NOT create a separate `families` table. Use the existing `family_id UUID` column on `profiles` as the shared identifier.

**Rationale**: The current schema already uses `profiles.family_id` as the family grouping key (present in `AuthState.parentData.familyId`). All existing code (realtime channel `family:{familyId}`, RLS policies, reporting queries) references this column. Creating a new `families` table would require a migration of all existing data and a rewrite of every foreign key. The `pairing_tokens.family_id` column will be a plain UUID that must match the parent's `profiles.family_id` — validated in RLS policy rather than a foreign key to a non-existent table.

**Alternatives considered**: TwoDevicePlan.md proposes `REFERENCES families(id)` — this is architecturally ideal but incompatible with the existing schema. Deferred to a future refactoring spec if a proper families table becomes necessary.

## Decision 4 — Token Generation: Client INSERT vs Server Function

**Decision**: The parent device directly INSERTs a row into `pairing_tokens` via its authenticated Supabase session (using the anon key + parent JWT). No Edge Function or server-side function is required.

**Rationale**: RLS policy `parent_write_pairing_tokens` restricts inserts to the parent's own `family_id`, providing sufficient server-side validation. Edge Functions add operational complexity (deployment, cold starts) with no security benefit here. The `token` UUID is generated by `gen_random_uuid()` in PostgreSQL — the client cannot forge a token it did not receive from the server response.

**Alternatives considered**: Supabase Edge Function — overkill for a simple INSERT with RLS. PostgreSQL function (RPC) — unnecessary given RLS covers the authorization requirement.

## Decision 5 — Manual Code Generation

**Decision**: The 6-digit manual code (`XXX-XXX`) is generated server-side by PostgreSQL: `LPAD(floor(random() * 1000000)::text, 6, '0')`. It is stored in `pairing_tokens.manual_code` and returned to the client with the INSERT response.

**Rationale**: Server-side generation ensures the manual code is unique per row and not predictable from client state. The parent displays it exactly as returned. The code is purely a human-readable alias for the UUID token — validation in Phase 2 will look up the token by `manual_code` within the family's unexpired tokens.

## Decision 6 — "Child Paired" Realtime Notification

**Decision**: The parent subscribes to Supabase Postgres Changes (CDC) on the `pairing_tokens` table, filtered to `family_id = eq.{familyId}`. When an UPDATE event arrives with `used_at IS NOT NULL`, the parent navigates to the dashboard.

**Rationale**: This is exactly the mechanism described in TwoDevicePlan.md Phase 1, and it is consistent with how the existing `familyChannel.ts` already uses Supabase Realtime. Postgres Changes CDC is reliable (not ephemeral like Broadcast) — the parent will receive the notification even if they briefly lost connectivity, as Supabase will re-deliver missed events on reconnect.

**Subscription filter**: `UPDATE` events only, on `public.pairing_tokens`, filter `family_id=eq.{familyId}`.

**Cleanup**: The subscription must be unsubscribed in the `useEffect` cleanup function (per constitution §API Hook Pattern).

## Decision 7 — Countdown Timer Implementation

**Decision**: Use a `useEffect` + `setInterval(1000ms)` that computes `remainingMs = new Date(expires_at).getTime() - Date.now()` on each tick. When `remainingMs <= 0`, call `generatePairingToken` to get new codes and reset the timer.

**Rationale**: Client-side countdown tied to `expires_at` (server timestamp) rather than a local start time. This means system clock drift affects the visual countdown but not actual expiry — the server validates `expires_at > now()` server-side in Phase 2. This is acceptable per spec FR-002 which defines expiry as "from the moment it was generated" (server time).

## Decision 8 — RLS Policies for pairing_tokens

**Decision**: Two policies on `pairing_tokens`:
- `parent_read_pairing_tokens`: `SELECT` for authenticated parents on their own family's tokens
- `parent_write_pairing_tokens`: `INSERT` for authenticated parents on their own family_id

The `UPDATE` policy (for Phase 2 when child consumes a token) is explicitly deferred to Phase 2 spec.

**Policy logic** (uses `family_id` match):
```sql
-- Read: parent sees tokens for their own family
USING (family_id = (
  SELECT family_id FROM profiles
  WHERE id = auth.uid() AND role = 'parent'
))

-- Write: parent inserts tokens for their own family
WITH CHECK (family_id = (
  SELECT family_id FROM profiles
  WHERE id = auth.uid() AND role = 'parent'
))
```

## Decision 9 — device_registrations Table Scope

**Decision**: The `device_registrations` table is created in the Phase 0 migration (as it is part of the shared schema) but is NOT populated in Phase 1. Phase 2 (child pairing) populates it when a child device completes the pairing flow.

**Rationale**: The table must exist before Phase 2 runs, but Phase 1 (parent QR screen) has no need to write device registration rows. Creating it now with Phase 2's RLS stub keeps the migration atomic with the `pairing_tokens` table.

## Decision 10 — Test Strategy for Phase 1

**Unit tests** (`tests/unit/pairingToken.test.ts`):
- Manual code format validation (6 digits, `XXX-XXX` regex)
- `PairingToken` TypeScript type shape
- Countdown timer helper logic (remainingMs calculation, zero-trigger)

**Integration tests** (`tests/integration/pairing.test.ts`):
- `generatePairingToken` inserts a row with correct TTL
- RLS: parent can SELECT their own family's tokens
- RLS: parent cannot SELECT another family's tokens
- RLS: unauthenticated user cannot INSERT/SELECT pairing_tokens
- Token uniqueness: two calls return different UUIDs
- `watchForChildPaired` returns an unsubscribe function (subscription lifecycle)

All integration tests use `HAS_CREDENTIALS`/`maybeDescribe` skip pattern.
